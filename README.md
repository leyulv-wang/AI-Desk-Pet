## 跑起来

### 最省事：双击两个文件

项目根目录有两个 `.cmd`，双击就行，不用开终端：

| 文件 | 作用 |
| --- | --- |
| **`启动桌宠.cmd`** | 启动。已经在跑的话不会开第二只，而是把已有窗口唤到前面 |
| **`关闭桌宠.cmd`** | 关闭。**连她拉起来的语音服务一起收掉** |

关闭脚本为什么要管语音服务：那玩意儿占着约 2.9G 显存。
如果桌宠是被强杀的（任务管理器 / `Stop-Process`），它来不及收，
语音服务就变成孤儿进程一直占着显存 —— 用户只会觉得「关了怎么显存没降」。
所以关闭脚本走的是 `taskkill` **不带 `/F`**（发 WM_CLOSE，让它正常退出），
等 10 秒还不退才强杀，并且强杀之后自己补刀收拾语音服务。

查看状态（也可以直接跑，不带参数就是 status）：

```bash
pwsh -File scripts/pet-ctl.ps1 status
# 桌宠：在跑（pid 24724）
# 语音服务：在跑（pid 5060）
```

`scripts/pet-ctl.ps1` 支持的参数：

```bash
pwsh -File scripts/pet-ctl.ps1 start              # 启动
pwsh -File scripts/pet-ctl.ps1 start -Foreground  # 前台启动，日志打在终端（排错用）
pwsh -File scripts/pet-ctl.ps1 stop               # 关闭
pwsh -File scripts/pet-ctl.ps1 stop -KeepVoice    # 关闭但留着语音服务（你自己起着调试时用）
pwsh -File scripts/pet-ctl.ps1 status             # 看状态
```

> 桌宠会在 `.userdata/pet.pid` 里写下自己的进程号，关闭脚本靠它认人。
> 这比「按命令行捞 electron 进程」可靠 —— Electron 有好几个子进程，
> 而且换个启动方式（`npm start` / 直接跑 `electron.exe`）命令行就不一样了。

### 三种关闭方式，随便哪种

1. **`关闭桌宠.cmd`**（或者 `scripts/pet-ctl.ps1 stop`）
2. **全局快捷键 `Ctrl+Shift+Q`** —— 不用去找那个小小的关闭按钮
3. **点窗口的关闭按钮** —— 关窗即退出

三种都会走同一套退出流程：关掉自己拉起来的语音服务 + 落盘还没整理完的对话记忆。
`Ctrl+Shift+P` 是显示/隐藏切换（不是退出）。

```bash

npm run setup        # 下载前端库 + Live2D 模型到本地（之后可离线运行）

> ```bash

**语音服务是桌宠自己拉的。** 开了 `tts.enabled` 且 `tts.gptsovits.autoStart=true`（默认），
桌宠启动时会在后台把 GPT-SoVITS 拉起来（模型要读 4.5G 进显存，约 10 秒），
聊天记录里会打印进度。它先立起来、嗓子随后到，不挡窗口显示。

都只是不出声 —— 打字聊天、记忆、历史一概不受影响。

快捷键 `Ctrl+Shift+P` 是显示/隐藏切换，可能被误按过。
缩放倍率会自动记住（右下角为锚点），太小就滚轮放大。

## 语音（L2）

> **当前用的是云端 MiniMax 声音克隆**，不是本地推理。下面「怎么接上的」那几节讲的是本地
> GPT-SoVITS 的方案，代码还在、随时能切回去（`tts.backend` 改一个词），
> 但默认已经换成云端。**换的理由和账**见本节末尾「为什么最后换成了云端」。

### 怎么接上的

音频由**本地** GPT-SoVITS 推理，用的是已经练好的芙宁娜 v4 权重：

```
GPT_weights_v4\芙宁娜_ZH-e10.ckpt            148 MB   GPT 语义模型
SoVITS_weights_v4\芙宁娜_ZH_e10_s950_l32.pth  72 MB   音色模型
```

- 权重配置写在 `voice/gptsovits.pet.yaml`（v4 + cuda + fp16）。
  **故意不复用整合包自带的 `GPT_SoVITS/configs/tts_infer.yaml`** —— 那个文件 WebUI 一开
  就会把它改回「底模 + cpu」，桌宠的音色就没了。
- `src/voice-server.js` 负责找整合包（支持「套两层同名目录」这种常见解压结构）、
  用自带的 `runtime/python.exe` 把 `api_v2.py` 拉到 `127.0.0.1:9880`。
  整合包不在默认位置就设 `GPTSOVITS_HOME`。
  桌宠启动时的自动拉起和 `npm run voice` 走的是**同一份代码**，行为不会走偏。

> **为什么子进程的 stdout 要重定向到文件，而不是走管道**
>
> 因为踩过一个很阴的坑：stdout 是管道时，一旦父进程被 kill，管道就断了。
> 而 GPT-SoVITS 每处理一个请求都要写一行日志，写管道抛 `OSError: [Errno 22] Invalid argument`，
> 被它自己那个宽泛的 `except Exception` 吞成 `{"message":"tts failed"}`。
> 结果就是**端口照样能连、TCP 探活一切正常，但每一句合成都 400** —— 服务活着，但已经是残废。
>
> 重定向到 `.userdata/voice-server.log` 之后，根本没有「管道断裂」这回事。
> 另外 `tts.js` 除了 TCP 探活还记着「最近一次真实合成结果」——
> 真进了残废状态，🔊 会变成 ⚠️ 并在对话里提示重启语音服务。
>
> 归属规则也是明确的：服务本来就在跑（你自己起的）→ 不碰、退出也不杀；
> 是桌宠拉起来的 → 退出时由它关掉。

### 语气是怎么选的

四步，每步都尽量早、尽量不额外花钱：

```
LLM 回复  [温柔]累了就歇会儿吧，我陪着你。
   ↓ ① 句首的情绪标签由 LLM 自己打 —— 零额外延迟、零额外成本
   ↓ ② src/emotion.js 解析（认 [开心]【开心】（开心） 多种写法 + 同义词）
   ↓ ③ src/voice-select.js 在「温柔」的 5 条参考里挑一条
   ↓ ④ 这条参考的语气会"传染"给合成结果
```

八个类别：**平静 / 开心 / 得意 / 温柔 / 无奈 / 生气 / 难过 / 惊讶**。

③ 的打分是加权相加（权重都在 `voice-select.js` 的 `WEIGHTS` 里，想调直接改）：

| 因素 | 权重 | 为什么 |
| --- | --- | --- |
| 句式对齐（问/叹/陈述/省略） | 4.0 | 问句语调上扬是跨语言通用的，**这条收益最大** |
| 字数接近 | 每字 1/14 | 参考和正文节奏接近，念着更自然 |
| 冷却（刚用过的不再用） | −7.0 | 避免连着两句听起来一模一样 |
| 随机扰动 | 0~1.2 | 同类回复之间也要有变化 |

**判定错了怎么办**：LLM 偶尔会忘标签，就用 `emotion.js` 的关键词规则兜底。
兜底走的是**不对称损失** —— 判错的代价不一样：

| 类别 | 门槛 | 为什么是这个门槛 |
| --- | --- | --- |
| 平静 | 0 | 本来就是默认值，判成它几乎没有代价 |
| 温柔 / 开心 | 2 | 判错只是味道淡一点 |
| 得意 / 无奈 / 惊讶 / 生气 / 难过 | 3 | 参考音频会把整句话念成哀乐或吵架，非常出戏 |

> 踩过的坑：兜底规则里曾有一条 `/^(……)/ → 难过 +1`，意思是「以省略号开头 = 有难言之隐」。
> 但芙宁娜大量句子就是以「……」开头的**说话习惯**，不是悲伤。结果一堆闲聊被兜底判成难过。
> 教训：**不要把标点习惯当成情绪证据**，除非那个标点本身就带情绪。

**为什么让 LLM 打标签，而不是再调一次模型做情绪分类**：她自己知道这句话是什么情绪，
而且标签就在流的最开头，第一个句子要送去合成时情绪已经定了。多一次 API 调用纯属浪费。
提示词里给了每个类别一句说明 + 正反例，特别是 **「得意 vs 生气」的分界**：
得意是**你占上风**（炫耀、俏皮挤兑），生气是**你被惹到**。撒娇式的小脾气用得意或开心。

**为什么用参数而不是只靠模型的「表情文件」**：VTS 系模型通常只有几个表情开关（芙宁娜这个只有脸红/爱心眼/生气），覆盖不了八种情绪；
而且不同模型的表情名千奇百怪（`F01` / `smile` / `exp_03`…），换模型就得重配。
Cubism 的**标准参数名**在所有模型上都一样，所以 `renderer/face.js` 直接推
`ParamEyeLSmile` / `ParamBrowLY` / `ParamMouthForm` 这些参数。
叠加用 `addParameterValueById` 而不是覆盖 —— 覆盖会把待机动作的眨眼和呼吸一起顶掉，
角色会变成一张死脸。

### 一段话被念成两种语气？参考音频必须整轮锁定

实测踩到过这个问题，而且**每轮必中**。

原因：GPT-SoVITS 的语气几乎完全由参考音频决定，换参考 = 换个人在念。
而参考选择器带「冷却机制」（刚用过的那条扣 7 分，避免连着两句听起来一样）。
如果**每句都独立选一次参考**，第二句打分时第一句刚用过的参考已经被扣分了，
必然挑到另一条 —— 于是一句话被念成上下两种语气。

复现出来长这样（`npm run voice:lock`）：

```
【温柔】a0595c67 → c97686b5   2 条  ← 上半句一条、下半句另一条
【平静】3ccfe5d9 → 80800ffd   2 条  ← 前一条是悲伤独白，后一条是「你们听我说话啊」
```

**修法**：一轮回复只在第一句时选一次参考，锁进 `speech.refId`，
后面所有句子强制复用；冷却只在**轮与轮之间**生效。

顺带把随机种子也锁了（`tts.gptsovits.seedLock`）：种子由「情绪类别 + 参考音频」推导，
是**确定值**，所以磁盘缓存照样命中，而同一条参考下所有句子的采样风格一致。

> **「那干脆整轮合成一次不是更好？」——量过了，并没有。**
>
> 用自相关估基频（F0），量前后半段的平均音高差：
>
> | 做法 | 前后半段音高差 |
> | --- | --- |
> | 分开合成（参考已锁定） | **1.98 半音** |
> | 一次合成整轮 | **1.97 半音** |
>
> 几乎没有区别。所以**不必**为了连贯性去牺牲「边生成边合成」的低延迟。
> `npm run voice:pitch` 可以自己复现这个测量。

### 切句的两条规则

`src/sentence.js` 是流式切句器，除了按标点切，还有两条不那么显然的规则：

1. **切点正好落在缓冲区末尾时先别发。** 流式输入里，终结符到的时候还不知道它完不完整：
   - `…` 可能是 `……` 的前一半（实测被从中间切开，变成「一句收尾 + 一句起头」）
   - `。` 后面可能还跟着 `」』`
   等下一个 token 再决定，代价几十毫秒；流结束时 `flush()` 会强制吐出来，不会卡住。
2. **短句（<6 字）先攒着跟下一句拼，一路拼到够长为止。**
   拿「嗯。」两三个字去合成，韵律会非常怪 —— 而且实测会**直接失败**，见下。

> **这条规则原来有个洞，代价是「张嘴先哑半秒」。**
> 旧写法是「短句 + 后面还有内容时，拼起来不超过 `maxChars` 就继续等」——
> 反过来说，**一旦拼起来超过 `maxChars`，那个短句就单独发出去了**。
> 于是一句真实的流式回复被切成：
> ```
> 「诶？」+「你、你居然学我说话！」+「「本神」这个词是……」
> ```
> 而 GPT-SoVITS 拿一两个字去合成很不稳，**实测「诶？」3 次里 2 次**
> 吐出近乎全零的片子：
>
> | | 正常片子 | 那个废片 |
> | --- | --- | --- |
> | 时长 | 1.4~4.8s | 0.40s |
> | 有声样本占比 | 91~98% | **15%** |
> | RMS（归一化后） | 0.0900 | **0.0023** |
> | 峰值 | 0.43~0.55 | **0.0295** |
>
> 而且它**完美躲过了当时那道「废片守卫」** —— 守卫判的是语速（字数/有声秒），
> 一段静音在语速上完全"正常"；更糟的是守卫被 `needChars >= 4` 挡着，
> 「诶？」只有 1 个字，**越容易出废片的短句越不会被检查**，正好反了。
>
> 两处都修了：`sentence.js` 不再发小段（`scripts/test-splitter.mjs` 守着），
> `tts.js` 的守卫扩成「时长 + 响度 + 有声占比 + 语速」四条判据（`npm run diag:dud` 守着）。

**同一个洞还有第二个入口，隔一次自检又冒出来了。** 这次是情绪标签：

```
[开心]陪你？这话该我说才对吧。……
```

`[开心]陪你？` 用 `.length` 数出来**正好 6 个字**，刚好越过 `minChars` ——
于是「陪你？」又被单独发了出去（标签要等 `acceptSegment` 才剥掉，切句器看到的还是带标签的原文）。
这一次更糟：3 次重试**全部失败**（有声占比 37% / 33% / 44%），最后放出去的是一段哑音。

所以「够不够长」不能数 `.length`，要用 `effectiveChars()` ——
**先去掉句首的括号标记，再数**。`sentence.js` 和 `emotion.js` 各有一套剥法，
`test-splitter.mjs` 里有一条断言盯着它们别走偏（8 个类别 × 3 种括号写法）。

教训：**同一个判据被用在两个地方时，得确认两个地方量的是同一件东西。**
「短句别单独发」这条规则本身没错，错的是"短"这个字在两处定义不一样。

还有一条是**剥情绪标签的位置**：切句器只吃**原始文本**，标签在句子切出来之后再剥。
一开始反过来做（先剥标签再喂切句器），结果流的前几个 token 是半截标签「[生」，
那时还认不出来、`cleaned` 等于原文；等标签补全后 `cleaned` 突然短了 3 个字符 ——
按 `cleaned` 长度记偏移就错位了，实测丢掉了「喂，同」三个字，还把 `[生气]` 念了出来。

### 开桌宠后第一句话不响？

修过。模型要读 4.5G 进显存（约 10 秒），而 LLM 可能 8 秒就回完话了 ——
第一批合成请求会在服务还没起来时发出去，全部 `fetch failed`。
现在合成前会 `await voiceServerReady`（有 90 秒超时兜底），日志里能看到：

```
[tts] 语音服务还在启动，这一句等她一下…
[voice-server] 已就绪（10s 起来，pid 26028）
[tts] 等待结束（2210ms）
```

### 为什么不整段合成完再放

GPT-SoVITS 合成一句要 1.5~2 秒。等整段回复写完再送合成，用户按下回车要等 3~4 秒才听到声音。

所以做成流水线：

```
LLM 流 ──► 切句器 ──► 合成队列（串行）──► 渲染层按序播放
           ↑ 第一句一完整就立刻入队，后面几句在她念第一句的时候并行合成
```

落盘缓存（`.userdata/tts-cache/`）：桌宠的回复大量重复，
同文本 + 同参考 + 同参数 = 字节完全一样，**命中缓存 1ms**，新合成约 1.6s。

### 口型为什么是真的

解码后用 WebAudio 拿到 PCM，按 30ms 一帧算 RMS，得到**这句话真实的响度曲线**；
播放时按当前播放位置查表驱动 `ParamMouthOpenY`。起音快收音慢，还做了相邻帧平滑。

比"说话时用正弦函数开合嘴"好在：那套和音频完全对不上 —— 闭着嘴的时候嘴在动、
拖长音的时候嘴在抖，一眼假。算包络是解码时顺手的事，免费且准确。

一条踩过的坑：`capturePage()` 从调用到真正抓像素有几百毫秒，说话时嘴型几十毫秒变一次，
所以**截图验证永远拍到闭嘴那一帧**，看起来像"嘴根本没动"。`petModel.holdMouth(v, ms)` 就是为这个加的。

### 情绪标签漏了怎么办

实测 `deepseek-flash` 有时会忘。两层兜底：

1. **兜底判定**：没标签就用关键词+标点猜（`emotion.guessEmotion`）。
   注意**必须等第一句完整**再猜 —— 前十个字信息太少，
   实测「哼哼，本神记性可是很好的」的前十个字「哼哼，本神记性可是」一个线索都没有，会误判成平静。
2. **历史自我纠正**：历史里存的是**带标签的原文**。
   这里踩过一个坑：一开始存的是剥掉标签的正文，结果模型在上下文里看到自己以前的回复
   全都没有标签，就有样学样地不打标签了，漏标率飙升。现在漏标的话会用兜底类别补一个再存，
   让上下文的示范永远 100% 规范，这个毛病会自我收敛。
   （记忆抽取仍然用剥掉标签的正文 —— 标签是格式噪音，不该变成关于用户的事实。）

### 她怎么说话：只说出口的话

**她要的是「像芙宁娜」，不是「在演一场戏」。** 这两个目标很容易被混成一个 —— 试过做成
「旁白 + 对白」混排的角色扮演写法：

```
[温柔]累就歇着，谁规定今天非得干点什么。*她把杯子搁在桌上，坐直了身子。*
      我泡杯热的给你，甜的也有。
```

**做出来了，然后被否掉了**，理由很干脆：用户想要的是**她足够像**，
不是**情景扮演**。加了旁白之后她更像一个在演出的角色，而不是一个在跟你说话的人。

所以人设里现在写的是反过来的硬要求：

> 你**只说你会说出口的话**。不要写旁白、动作、神态、心理描写，
> 不要用星号或括号标注动作 —— 你说的话会被念出来，写出来的旁白不会，只会变成一串噪音。
>
> 想让对方感觉到你的动作和神态，就**用说的**：
> 不说「\*她假装在整理袖口\*」，说「别看我，我袖子歪了。」
> 不说「\*她愣了一下\*」，说「……咳。你刚才说什么？」

最后那两条**示范**是重点。这个项目反复验证过同一件事（见下面「例子比禁令强得多」）：
写「不要写旁白」是没用的，写「**改成这样说**」才有用。

效果（4 句 60 字，一个旁白都没有）：

> 你：今天写代码写得有点烦
> 她：「又是这句。阿远，你今天这台本翻来覆去就一页？」
> 　　「行，那我不问你代码的事了。」
> 　　「茶还温着，要不要我放张唱片？」
> 　　「比盯着报错强。」

「台本」「唱片」「茶」还是她的词，剧目化句法（把日常拆成选角/布景/谢幕）也还在 ——
**像不像她取决于用词和节奏，不取决于有没有旁白。**

#### 那 `src/spoken.js` 还留着干什么

**当安全网。** 人设说了不许写旁白，但模型偶尔还是会漏一个 `*……*` 出来 ——
这时候它仍然不会把星号念给你听。同理 `emotion.stripAllTags()` 也留着：
模型偶尔会在句子中间又打一个 `[平静]`，那个位置原本的剥标签逻辑不管。

规则没变，只是从「旁白必须用星号包起来」变成了「**万一有星号，别念**」：

1. `*星号*` 里的内容不念（`**双星号**` 也算一对）
2. 引号（`「」『』“”`）只是写法，剥掉外壳留内容

#### 为什么是「剥星号」而不是「抽引号」

直觉做法是「只念引号里的」，但**流式下这个判断做不对**：回复常常先写一段旁白再开口，
而旁白到的时候我们还不知道后面有没有引号 —— 要么先憋着不出声（首句延迟变长），
要么赌一把（赌错就把旁白念了）。

改成「旁白用星号标记，其余都念」之后，逐字符就能判，不需要预读；
跨句的星号也能靠一个 `inStar` 标志接上（`*旁白` 在上一句、`结束*` 在下一句，实测过）。

代价是人设里必须硬性要求「旁白一律用星号」，漏了这条就会把旁白念出来 ——
所以 `npm run test:spoken` 专门守着这件事（27 项断言，含跨段星号、整段旁白、
未闭合星号、`**双星号**` 这些边界）。

**还有一个更阴的漏法，实测踩到过**：模型有时候会在**一轮回复中间**又打一个情绪标签 ——

```
[温柔]我不催你。*她把牌推到一边。*[平静]茶会开场了，你是唯一的主客。
                                  ↑ 这个标签不在句首
```

`extractTag` 只认句首标签（这是对的，正文中间的方括号是剧情内容），
于是第二个标签原样漏进语音，用户会听见「方括号 平静 方括号」。
修法是 `emotion.stripAllTags()`：**任何位置**的标签都剥，但括号内容必须确实是一个
已知情绪词才删 —— 所以正文里的 `[注]`、`[1]` 都留着。

#### 一段被否掉的弯路：旁白

**做过，被否了，记在这儿免得再走一遍。**

当时的推理是：角色扮演的效果来自「卡 + 世界书 + 历史 + **允许长回复和旁白**」，
前两样已经有了，差的只是第四样，于是把回复放成「旁白 + 对白」混排。

**推理没错，但方向错了。** 用户的原话是：

> 我之前想要的角色扮演只是她**足够像**，而不是包括**情景扮演**

也就是说，「像芙宁娜」和「演一场戏」被他分得很清楚。加了旁白之后，
她更像一个在舞台上表演的角色，而不是一个**在跟你说话的人** —— 而这只桌宠是后者。

这一轮的产出没有浪费，但**降级成了安全网**：

| 做出来的东西 | 现在的角色 |
| --- | --- |
| `src/spoken.js`（剥星号、只念对白） | 安全网 —— 人设不许写旁白了，但万一漏一个 `*…*`，仍然不会念出来 |
| `.narration` 灰斜体样式 | 同上，真出现旁白时能一眼认出来 |
| `emotion.stripAllTags()`（剥句中标签） | **仍然必需** —— 和旁白无关，模型本来就会在句中乱打标签 |
| `logText()` 压空行、`.sub-line` 放宽到 6 行 | **仍然必需** —— 见下面「显示这一层」 |

**教训：把「像不像」和「演不演」当成两件事问清楚。**
我按「角色扮演」这个词的字面意思做了一大套，而对方要的其实是前一半。

#### 显示这一层踩过的三个坑

（这三个坑是角色扮演那轮暴露出来的，但**旁白去掉之后它们依然存在** ——
模型照样会打句中标签、照样会留空行，所以修法都留着。）

**① 空行吃掉一整行。** 模型习惯在段落之间空一行（`\n\n`），
而气泡是 `white-space: pre-wrap` —— 那个空行**实打实占掉一整行高度**。
`logText()` 里把 `\n{2,}` 压成一个换行。压缩放在显示层而不是入库层：
历史里保留模型自己的排版，而且这样连旧记录也一起修好了。

**② 字幕被裁在框外。** 用户的原话是「第二行可能会落到对话框外面」。
根因是 `.sub-line` 的 `max-height: 4.6em` —— 按 13px 字号算就是 **3.07 行**，
而角色扮演的回复是「旁白 + 台词」混排的，旁白稍微一折行就超过 3 行，
台词被 `overflow: hidden` **直接裁掉**。现在放到 9.1em（6 行）。
> 顺带一个教训：我一开始以为用户说的是聊天日志气泡（`#chat-log`），
> 改了半天没用 —— 那个面板**默认是隐藏的**（`offsetHeight = 0`）。
> 真正显示回复的是底部字幕 `.sub-line`。**先量再改**，
> `scripts/debug-subtitle.js` 就是那次留下的（它会打印盒子高/内容高/能放几行）。

**③ 句中的情绪标签显示出来了。** 和语音、记忆那边是同一类问题：
模型偶尔在旁白之后又打一个 `[平静]`，`stripTag()` 只认句首那个，
于是气泡里显示成「…她把牌推到一边。[平静]我刚才一直在想…」。
现在任意位置的标签都剥，但括号内容必须确实是已知情绪词才删 ——
所以正文里的 `[注]`、`[1]`、`[王后的荣冠]` 都留着。

> 另外还有个自己埋的雷：`pushLog` 和字幕共用过一个 `displayText()`，
> 而它会把 `*星号*` 剥掉 —— 于是 `appendRich` 永远匹配不到旁白，**样式整套失效**。
> 现在拆成 `logText()`（保留星号，给气泡上色）和 `displayText()`（剥星号，给字幕）。
> 教训：**同一个函数被两个地方用时，先想清楚两边要的是不是同一样东西。**

### 关于「能不能把酒馆的 API 拉出来」

问过这个问题，查完的结论是：**拉不出来，但也不需要。**

SillyTavern 1.18 的服务器端（`src/`）**没有任何 prompt 组装代码** ——
它只做两件事：管文件 + 代理 LLM 请求（`/api/backends/chat-completions/generate`
收的是**已经拼好的 messages**）。真正让它角色扮演好的那套东西
（角色卡注入、世界书触发、Prompt Manager 编排、上下文模板、正则脚本）
全在前端 `public/scripts/` 里跑，是浏览器里的 ES 模块，`window` 上也没挂。

官方确实支持 **server plugin**（`enableServerPlugins: true`，路由挂在 `/api/plugins/{id}/…`），
但插件里拿不到 `generateQuietPrompt` —— 那是前端的函数。能做的只有「自己拼 prompt 再转发给 LLM」，
等于白折腾。

**而且酒馆效果好并不是因为什么秘密配方。** 翻了它的默认预设
（`default/content/presets/sysprompt/`，13 个）之后发现，"Roleplay - Immersive" 全文就一句：

> Write one reply only. Do not decide what {{user}} says or does.
> Write at least one paragraph, up to four. Be descriptive and immersive...

所以它的角色扮演质量来自四件事，**没有一件是玄学**：

| | 酒馆怎么做的 | 我们 |
| --- | --- | --- |
| 角色定义 | 角色卡（description / personality / scenario） | ✅ 已有（`character-card.js` + `characters/furina.json`） |
| 世界知识 | 世界书按关键词触发 | ✅ 已有（`lore.js`，18 条） |
| 上下文 | 历史原样回灌 | ✅ 已有（`history.js` 分层归档 + `memory.js`） |
| **允许长回复和旁白** | 一段到四段，可以写动作 | ✅ **刚补上**（`spoken.js` + 人设的【旁白与对白】） |

前三样我们早就有，差的只是第四样。补上之后就没有「必须走酒馆」的理由了 ——
而且我们还有酒馆没有的：**TTS 只念对白**、真实音量口型、记忆抽取、情境反应。

> 如果以后真想让桌宠当酒馆的前端，技术上唯一可行的路是
> **开一个隐藏窗口加载酒馆前端、用 `executeJavaScript` 调它的 `generateQuietPrompt`**。
> 那是 100% 保真的，但要跑两个进程、一个完整浏览器，而且酒馆一升级就可能碎。
> 目前判断不划算 —— 想要的话说一声。

### 角色档案与人格调优

角色是 `characters/<id>.json`，换角色只改 `config.json` 的 `character` 字段，代码一行不动。
人格正文、情绪语音开关、L2D 表情映射都在里面。

**人格 prompt 有个反直觉的地方：例子比禁令强得多。**

踩过的坑：芙宁娜每句都自称「本神」，而 prompt 里其实**写了**禁令
（「偶尔自称『本神』，但不要每句都自称，会很腻」）。禁令完全没用 ——
真实对话 4/4 条都在说。原因是三重的：

1. **我在「性格」段里亲手示范了。** 有一行写「嘴上说『本神只是恰好有空』」，
   本意是描述她嘴硬心软，但模型看到的是「这个角色说本神」。
2. **否定式指令天生弱。** 同一段里还有「不要每次都提自己是水神」，她照提不误。
3. **历史会自我强化。** 她过去的回复条条带「本神」，那比 system prompt 更靠近、
   更具体，模型会照着学。（和「情绪标签漏标」是同一类 bug）

改法：**把禁令换成可数配额 + 正反对照样例**，并且把性格段里那个示范改成不用「本神」的写法。

效果（`npm run eval:persona`，同样 16 个样本、同一份真实历史）：

| | 自己写的（第一版） | 自己调过配额 | 用社区资料重写后 |
| --- | --- | --- | --- |
| 「本神」出现率 | **88%**（14/16） | **25%**（4/16） | **13%**（2/16） |
| 一句里超过一次 | 3 条 | 0 条 | 0 条 |
| 最长回复 | — | — | 59 字 |

调完人格**别靠肉眼看几条回复判断**，跑这个：

```bash
npm run eval:persona                      # 默认角色，带真实历史，8 个固定问题
npm run eval:persona furina --runs=2      # 每边 16 条，统计更稳
npm run eval:persona furina --no-history  # 排除历史影响，只看 prompt 本身
```

它会统计指定口癖的出现率、超标条数、回复长度、情绪分布。
想 A/B 对照就复制一份角色文件装旧 prompt，把 id 当参数传进去对比。

### 人设资料：为什么最后用的是社区的东西

自己写的那份档案调到「本神 25%」就卡住了 —— 数字能压下去，但**她的味道是编出来的**。
自己写的性格形容词（「戏剧化、爱装、嘴硬心软」）谁都能写，模型照着演出来的是一个通用傲娇，
不是芙宁娜。真正稀缺的是两样东西：**她实际怎么说话**，和**她对具体话题的现成反应**。
这两样社区里已经有人做了好几年。

现在用的是这两份（**都只自己用，不入库**，见 `.gitignore`）：

| | 提供什么 | 授权 |
| --- | --- | --- |
| [Furinelle/furina](https://github.com/Furinelle/furina) | 中国人设底子。12 份结构化角色资料，语气部分**按官方实装语音逐字核验** | **MIT** |
| [Bronya Rand 的角色卡](https://bronya-rand.github.io/reimagined-couscous/furina) | 18 条情境反应（世界书），译成中文后放在 `assets/lore/` | 作者保留著作权 |

**Furinelle 那份最值钱的一条**：它按官方语音核验出「本神」是**舞台残留 / 滑口 / 自嘲套用**，
默认自称是「我」，而且给出了最高识别度的写法 —— **句内自我修正**：

```
本神今天心情极好——好啦，我心情很好。
本神——咳，我，刚才说到哪了。
```

这比自己压出现率高明得多：不是「少说」，是**说了之后被自己察觉到**。
实测 16 条里出现的 2 次「本神」全都长这样。

时期选的是**卸任后**（魔神任务第四章第五幕之后）—— 她不再是水神，以凡人身份生活。
桌宠场景放这个时期最自然：住你电脑里过普通日子，比「水神微服私访」合理得多。
人设里明确写了「不会主动提白淞镇/预言/五百年」这类沉重旧事，免得闲聊时突然沉重。

### 情境反应：她会接你的话茬

`assets/lore/<角色>.scenes.json` —— 她对具体话题的现成反应，由 `src/lore.js` 按关键词注入。

为什么单独做一套、而不是丢进记忆检索：

| | 记忆（`memory.js`） | 情境反应（`lore.js`） |
| --- | --- | --- |
| 管什么 | **你这个人**（叫什么、在做什么、上次聊到哪） | **眼前这个话题**（下雨了、早上好、好无聊） |
| 匹配方式 | BM25 ⊕ 向量，模糊召回 | **关键词**，命中就是命中 |
| 为什么这样 | 记错一件小事没人在意 | 「她为什么突然说起下雨」很出戏，必须可预测 |

零成本，不调 embedding。实测：

```
你：今天下雨了，好烦啊，不想写代码了
她：[无奈]又是下雨……好吧，这回水位真不涨了，放心。这种天气就适合窝着，
    来杯热的配马卡龙，比对着屏幕生闷气强多了。
```

—— 注入了「下雨」那条反应，但**没有照抄**（那条原文是「哎呀，雨下得真大！……等等，水位没在涨吧？」），
而是借了调子自己说。这是 `block()` 里那句「参考这个反应，保持同样的调子，也可以自己说」的功劳。

两个已知的坑，都处理了：

- **英文 key 的子串误伤**。卡里的 key 有 `Fun`、`Rain` 这种短词，子串匹配的话
  `function` 会命中 `Fun`、`brain` 会命中 `Rain`。所以纯 ASCII 的 key 卡词边界，中文的走子串。
  （`npm run test:lore` 里专门测了这几条。）
- **触发词挂错条目**。LLM 分触发词只看语义相关，不看场合对不对 ——
  它把「蛋糕」挂到了「下午好」那条上，于是你晚上给她带块蛋糕，她会回「下午好呀」。
  这类错误在 prompt 里说不清楚（每次生成换一批词），所以在 `import-card-lore.mjs`
  里列了个 `KEY_FIXES` 钉死。

没有 `assets/lore/` 是正常情况，不影响任何东西。

### 角色卡（社区格式）支持

`config.json` 的 `character` 除了 `characters/<id>.json`，也可以指向一张**角色卡**：

```
characters/cards/<id>.png      ← 社区标准格式（PNG 里塞 base64 JSON），放这儿就自动生效
characters/cards/<id>.json     ← 没图的纯数据版也行
```

分工是**卡管人格、json 管接线**：

| | 谁提供 | 为什么 |
| --- | --- | --- |
| 她是谁（性格、背景、说话样例） | 角色卡（有卡时覆盖 json 里那份） | 这是社区沉淀的东西，卡片规范定义的 |
| L2D 表情映射、tapLines、情绪语音开关 | `characters/<id>.json` | **卡片规范里根本没有「Live2D 表情映射」这个概念，也不该有** —— 那是每个前端自己的事 |

所以换卡不用动接线。卡里还能用 `personaAppend` 追加自己的修正。

```bash
npm run card:inspect -- "<卡文件>"           # 看卡里到底装了什么
npm run test:card                            # 读卡 + 转 prompt 的回归测试
```

**实测的一个意外结论**：那张英文芙宁娜卡（质量很高，description 4400 字）
转成桌宠 prompt 后只抽出 **0 条对白样例** —— 因为它的台词全是几百字的角色扮演叙述，
没有一句是「能说出口的话」。这正是**卡是给文字角色扮演写的，而桌宠是要用嘴说的**：

- 卡里的 `*动作描写*` 会被 TTS 念出来（「星号 她轻轻笑了笑 星号」）
- 卡里的回复动辄几百字，合成要等十几秒
- 卡的 `scenario` 以为你在提瓦特，而用户只是在写代码

所以 `character-card-prompt.js` 干的不是「抄」，是**提取**：剥掉动作描写、
只挑短台词当样例、再补上我们自己写的「场景」和「输出格式」两段硬约束。

### 情绪不连贯？量出来的结论：换参考 = 换嗓子

这是最难查的一个问题，前后修了三轮。前两轮修的是「一轮内换参考」和「参考库情绪混」，
但反馈仍是不连贯。第三轮不猜了，直接量（`npm run diag:prosody`）：

```
同一条参考、同一句话，重跑三次   →  输出逐字节相同（种子锁定了，噪声为 0）
换成同类别里的另一条参考        →  音高差 5.9 半音（接近三全音）
                                   语速差 1.9 倍
                                   响度差 2.6 倍
```

**换一条参考 = 换一个嗓子。** 而当时的冷却机制是**每轮都强制换参考**的
（选择器带「刚用过的扣 7 分」，每类只有 5 条，几轮下来全被扣一遍 → 必然轮换）。
于是她每回复一句就变一次声 —— 这就是「情绪不连贯」。

三个修法，每个都有测得的数字兜底：

| 措施 | 效果 |
| --- | --- |
| `tts.referenceMode = 'fixed'`（**当前选择**）—— 整只桌宠只用一条参考 | 音高/语速/响度**全程零跳变** |
| `tts.referenceMode = 'sticky'` —— 每个情绪类别各锁一条 | 同类别 1 条参考 ✅，声音只在情绪变化时才变 |
| `tts.normalizeLoudness` —— 输出 wav 按 RMS 归一化 | 响度极差 **2.6 倍 → 0** |
| 保留 `rotate` 模式做对照 | 需要同类内多样性时可以切回去，但要接受上面那些数字 |

> **顺带排除的两个嫌疑**：不是分类太多，也不是模型的问题。
> - 「分类太多」—— 8 个类别各自的参考在类别内是固定的一条；跨类别的音高差约 4.6 半音，
>   那部分是**该有的**（无奈的语气本来就比温柔低沉）。
> - 「模型的问题」—— GPT-SoVITS 在种子锁定的情况下输出**完全确定**，重跑噪声为 0。
>   `deepseek-flash` 只影响情绪**标签**，不影响声音。
>
> 还有一件事本来担心、量完发现不用担心：**一句话拆成多段合成，段间音高跳变只有 0.45 半音**
> （自然语调范围）。所以「按句切开、逐句合成、70ms 间隔」这条流水线本身不制造断裂。

**代价**：sticky 模式下每类只用得到 1 条参考，库里另外 4 条是备选和以后换风格用的。
换来的是「同一种情绪永远同一个嗓子」。

### 最终选择：`fixed` —— 就固定用一条参考

sticky 修掉了「一句一换嗓子」，但**跨情绪**那 4.6 半音的差还在：
她说「难过」和说「开心」是两个音区的人。而「平静」池 122 条里
**没有一条是真正平淡的**（音域最小 6.05 半音、中位 9.35，自然平静说话是 3~6）——
素材全是游戏剧情和战斗台词，都在演。所以「按情绪换参考」带来的**不一致**，
远大于它带来的**情绪准确度**。

于是直接固定一条。做法：

1. `npm run audition` 生成候选，人工听完挑一条（**这一步不能省**，测得出数字挑不出好听）
2. `config.json` 里填 `tts.referenceMode: "fixed"` + `tts.fixedRef: "<clip id>"`
3. `npm run check:fixedref` 验证

当前用的是 `7cd3e85678f2c4ef`（温柔，6.16s）：

> 「你愿意和我一起去吗？偶尔停下冒险的脚步听一段故事，也不错吧？」

挑它是因为它**音域窄、语速平、没有明显表演痕迹** —— 这类素材当参考时，
合成出来的句子最不容易带上一股借来的腔调。

`check:fixedref` 查五件事，缺一不可：

| | 查什么 | 为什么 |
| --- | --- | --- |
| ① | config.json 里两个字段都填对了 | 它读的是**真实配置文件**，不是自己拼一份 —— 自己拼配置的脚本只能证明代码写对了，证明不了你文件填对了 |
| ② | `fixedRef` 那条确实在 `library.json` 里 | 填错的 id 会静默回落 sticky，不查就发现不了 |
| ③ | 8 个情绪类别 × 任意句子**全部**指向同一条 | fixed 的全部意义就在这里 |
| ④ | 真实合成一句「生气」的话，回来还是那条参考 | 逻辑层对了不等于合成路径也走对了 |
| ⑤ | `fixedRef` 填错 / 留空时回落 sticky 且不崩 | 反面用例，防止「改了配置就白屏」 |

```bash
npm run check:fixedref              # 含真实合成（要先 npm run voice）
npm run check:fixedref -- --no-synth  # 只查逻辑，不用开语音服务
```

> **fixed 之后情绪丢了吗？没丢。** 丢的只是「借来的那点语气」：
> 表情（模型自带 expression + 标准参数，见 `src/renderer/face.js`）和
> 标点决定的语调起伏（`src/sentence.js` 的 `pauseAfter`）都还在。
> 情绪标签仍然照常解析、照常驱动表情，只是不再换嗓子。

**换参考只改 `tts.fixedRef` 一个字段，代码不用动。**

### 「像一句一句蹦出来，停顿怪」——根因是每段自带的静音

实测真实会话的 19 段音频，发现每段合成出来都自带**长短不一的头尾静音**：

| | 实测 |
| --- | --- |
| 段首静音 | **0.07 ~ 0.71s（乱跳）** |
| 段尾静音 | ~0.22s（稳定） |
| 播放层固定间隔 | 70ms（写死的） |
| → 实际句间停顿 | **0.36 ~ 1.00s** |

自然说话的句间停顿是 0.2~0.4s。所以实际停顿是自然的 2~3 倍，而且因为首部静音乱跳，
**忽长忽短** —— 这正是「一句一句蹦出来」的来源，也顺带造成「忽快忽慢」的听感
（节奏被不规则的空档打碎了，即使咬字速度本身没变）。

**修法两半：**

1. `tts.trimSilence`（`src/tts.js` 的 `postProcessWav`）—— 裁掉头尾静音，
   只留 40ms / 90ms 余量保护起音和收音。
2. 停顿改由**句尾标点**决定（`src/sentence.js` 的 `pauseAfter`）：

| 句尾 | 停顿 | 为什么 |
| --- | --- | --- |
| `……` | 380ms | 欲言又止，留白最长 |
| `？` | 300ms | 问完等对方 |
| `；` | 280ms | 分句 |
| `。` | 260ms | 陈述 |
| `！` | 230ms | 语气急，接得紧 |

修完实测：

```
首静音 0.03~0.05s   尾静音 0.07~0.09s   停顿 230~380ms（由标点决定）
响度   全部 0.09（修前 0.0487~0.1255）
```

### 语速「忽快忽慢」：一个失败的尝试，和一个成立的结论

先量清楚：同一句话换不同参考，输出语速 2.75~6.29 字/秒（**2.29 倍**）。
而 `speed_factor` 是线性的（实测 1.05→0.8 时 3.55、1.0 时 4.41、1.3 时 5.64 字/秒）。

于是很自然会想：**先用一句固定的探测句测出每条参考的语速，再按比例补偿**。
我实现了，然后量了结果 —— **不成立**：

| 参考 | 探测句测得 | 实际那句 |
| --- | --- | --- |
| 难过 d27bb7f4 | 3.57（最低） | 2.82（最低）✅ |
| 温柔 494396d3 | 6.79（最高） | 6.29（最高）✅ |
| **平静 f062c823** | **6.12** | **2.75** ❌ |

排序大体成立，但被「嗯，我在听，你说吧。」这种**带长语气词的短句**打崩 ——
一个拖长的「嗯」就把整句的语速拉下去，而探测句里没有这种情况。
加宽 clamp 后极差没改善（2.29 → 2.20 倍），整体还被拖慢三成。

**所以这个功能默认关闭**（`tts.rateCalibration: false`），代码和失败数据都留在
`src/tts.js` 里当记录 —— 一个「看起来在工作、实际更糟」的机制比没有更坏。

**成立的结论**：
- **一句之内咬字速度是稳的**：实测同一轮回复 3 段的语速 4.07 / 4.51 / 4.32 字/秒，极差 0.44。
- **跨情绪的速度差是应该有的**（激动本来就说快），sticky 之后同类情绪速度恒定。
- 感知上的「忽快忽慢」主要来自上面那个**不规则停顿**，已修。
- 要整体调快慢，改 `tts.gptsovits.speedFactor`（线性、立即生效）。

### 为什么最后换成了云端（MiniMax 声音克隆）

上面那几节都在跟**同一个结构问题**搏斗：GPT-SoVITS 里**一段参考音频同时决定音色和语气**。
所有修法（sticky / fixed / 挑参考 / 语速校准）都是在「让参考别乱动」，
本质是绕，不是解。而且它还占 2.9G 显存、合成要 2~8 秒、偶尔吐哑音。

MiniMax 把这两件事**拆开了**：

| | 管什么 | 怎么给 |
| --- | --- | --- |
| `voiceId` | **音色** | 克隆一次，锁死 |
| `emotion` | 语气 | 每次合成可以给（我们默认不给） |

所以「换参考 = 换嗓子」这个问题**根本不存在**。实测延迟 0.74~0.96 秒，
比本地快 3~10 倍，而且不吃显存 —— 本地那个 2.9G 的语音服务不用起了。

#### 实测数据

| | MiniMax（2.8-turbo） | 本地 GPT-SoVITS |
| --- | --- | --- |
| 合成延迟 | **655~1067ms** | 1947~8046ms |
| 显存 | 0 | 2.9G |
| 音色稳定性 | 锁在 voiceId 上 | 换参考就换嗓子（5.9 半音） |
| 复现性 | 每次略有不同 | 种子锁定，逐字节相同 |
| 音色相似度（LTAS） | 0.873 | 0.962 |

> **LTAS 那一行别误读**：本地 0.962 更高，是因为它的参考音频
> **就是**克隆源里的一条（`7cd3e856`）—— 相当于开卷考试。
> 这个指标只用来排掉「克隆根本没生效」，不是「像不像本人」的裁判。
> 排掉了吗？排掉了：克隆 0.873 vs 系统女声 0.783 vs 男声 0.640。

#### 选哪一档：turbo，不是 hd

| 模型 | 单价 | 延迟 |
| --- | --- | --- |
| `speech-2.8-hd` | ¥3.50 / 万字符 | 811~1848ms |
| **`speech-2.8-turbo`** | **¥2.00 / 万字符** | **655~1067ms** |

**便宜 43%，还更快，而且听不出差别。** 对比脚本 `npm run compare:tiers`。

#### 账要这么算

计费口径有个坑：**1 个汉字算 2 个字符**，标点/字母/空格各算 1 个。
所以一句 60 汉字的回复 ≈ **125 计费字符** —— 按字数算会差一倍。

| 每天轮数 | 每月计费字符 | turbo | hd |
| --- | --- | --- | --- |
| 10 | 37,500 | ¥7.5 | ¥13.1 |
| 30 | 112,500 | **¥22.5** | ¥39.4 |
| 50 | 187,500 | ¥37.5 | ¥65.6 |

> **资源包对个人不划算**：最小套餐 ¥630 / 200 万字符 / **1 个月有效**。
> 中度使用一个月才 11 万字符，会用掉不到 6%。按量计费才是对的。
>
> 实测这一整套对比（40 多句、约 2000 计费字符）总共花了 **¥0.4~0.7**。

#### 代价，说清楚

1. **参考音频要上传到 MiniMax 的服务器**。这是「只自己用」边界的一次让步 ——
   本地方案里文件从不离开本机，云端方案里它离开了。上传的是游戏语音，
   还叠着声优的人格权，属于法律灰区（个人自用一般没人管，但别对外分发）。
2. **每次合成略有不同**（云端不接受 seed）。本地是逐字节可复现的。
   实测同一句话跑 13 次，音高分成两堆（33 左右 11 次、24 左右 2 次）——
   偶尔会低一个八度附近说话，不是错觉。
3. **要联网**。断网就没声（本地方案断网照说）。

#### 怎么接的

`tts.js` 的后端是可插拔的，现在有三条：`minimax` / `gptsovits` / `siliconflow`。
换回去只改 `config.json` 的 `tts.backend` 一个词，其它代码一行不动。

云端这条路和另外两条有个**根本区别：不需要参考音频**。所以：

- 不需要参考库（`library` 为空也能出声）
- 不锁参考（那边根本不存在这个问题）
- 种子没意义（云端不接受 seed）

但**废片守卫和后处理照旧** —— 上面第 2 条说了它偶尔会跑偏，不能假设它永远正常。

克隆的三步（脚本都在）：

```bash
node scripts/prepare-clone-audio.mjs --category=温柔   # ① 从参考库拼 ≥10 秒的克隆源
# ② 上传 + 克隆（见 .userdata/minimax-clone.json 里记的 file_id）
node scripts/check-clone-identity.mjs <源音频> <克隆输出> <系统音色>  # ③ 验证克隆真的生效
```

> 两个坑：上传的 `file_id` 会过期；克隆出来的 voiceId **7 天不用会被删**。

### 一个更根本的限制：语气是模型学出来的，不是参考带出来的

修完 sticky 之后我又量了「参考音频的音域宽窄，会不会影响输出的戏剧化程度」：

| 参考自身音域 | 输出音域 |
| --- | --- |
| 6.03 | 8.07 |
| 6.94 | 10.41 |
| 8.35 | 8.16 |
| 8.46 | 8.82 |
| 10.26 | 10.54 |

**不管参考是 6 还是 10，输出都稳定落在 8~10.5。** 参考的影响很弱、也不单调。

而且试过两个本该有用的旋钮，**都没用**：

| 旋钮 | 输出音域 |
| --- | --- |
| `temperature` 1.0 / 0.8 / 0.6 / 0.4 | 8.16 / 8.62 / 7.50 / 7.46 |
| `sample_steps` 16 / 24 / 32 | 7.88 / 8.16 / 8.02 |

结论：**戏剧化的语气是芙宁娜 v4 权重从训练语料里学到的** ——
那 1139 条全是游戏剧情/战斗台词，模型学到就是这个风格。
推理阶段没有旋钮能把它压平，换参考也不行。

> 想真正改变语气风格，只有两条路：用更平淡的语料**重新微调**，
> 或者**接受这就是芙宁娜的说话方式**。详见「已知限制」。

### 测「像不像」：语调指标会误导

选音色的时候踩过一个**方法论上的坑**，值得单独记。

我用「F0 + 音域」当相似度，跑了一轮配置扫描，算出某个 MiMo 配置（0.40）
比 MiniMax（0.44）更像。**用户听完直接否了：MiniMax 明显更像。**

错在哪：F0 和音域量的是**语调起伏**，而「像不像本人」的主体是**音色**。
语调可以调（一条指令的事），音色调不了（那是模型学出来的）。
**拿语调指标当相似度，等于用身高去判断双胞胎。**

后来换成 **LTAS（长时平均频谱）** 量音色（`npm run timbre:check`），结论又反了 ——
指标说 MiMo 最好的一条（0.92）比 MiniMax（0.89）更像，但耳朵还是判 MiniMax。
**指标和耳朵不一致时，耳朵赢。**

但指标量到了一件**耳朵容易忽略**的事：

| | 音色相似度 |
| --- | --- |
| MiMo 同配置两跑 | 0.63 / 0.75 —— **差 0.29** |
| MiniMax 两条 | 0.876 / 0.887 —— **差 0.01** |

**MiMo 的音色不稳定。** 峰值更高，但会跑出坏的。桌宠每天几十次，
撞上坏的那条就出戏 —— **稳定比峰值更重要**，这才是选 MiniMax 的真正理由。

所以「像不像」的度量顺序是：

1. **LTAS 音色相似度** —— 排掉明显不像的
2. **稳定性**（同配置多跑几条看方差）—— 排掉会跑偏的
3. **剩下的由耳朵定** —— 韵律、咬字、说话习惯是指标量不到的那一半

> 一句话教训：**先搞清楚你要量的是什么，再去选指标。**
> 当时想着「像」就去量了个听起来相关的（语调），实际要量的是音色。

### 测量工具本身踩过的坑

上面那些数字背后有个教训：**我用来判断「音域」的估音器一开始是错的，而且错得很有欺骗性。**

自相关估基频有两个经典陷阱，我两个都踩了：

1. **归一化方向反了。** 第一版写 `sum / (n - lag)`，想让不同 lag 可比 ——
   结果 lag 越大除的数越小、分数越高，**系统性地偏向长 lag**，
   也就是把基频估成一半（低八度）。音域因此被虚报近一倍。
   正确做法是归一化互相关 `Σx[i]x[i+lag] / sqrt(Σx[i]²·Σx[i+lag]²)`，
   并且取**第一个足够强的峰**而不是全局最大（纯周期信号在 T、2T、3T 处都是峰）。
2. **验证信号自己写错了。** 写 FM 测试音时用了 `sin(2π·f(t)·t)`，没有对频率积分 ——
   瞬时频率实际是 `f(t) + t·f'(t)`，那个 `t·f'` 项会随 t 失控。
   结果 ±1 半音的摆动被测成 13.6 半音，差点让我得出错误结论。

现在 `scripts/lib/wav-prosody.mjs` 里那份估音器**通过已知音高的自检**：

| 设定摆动 | 实测音域 | 理论值（1.902×A） |
| --- | --- | --- |
| ±1 半音 | 1.9 | 1.90 |
| ±2 半音 | 3.8 | 3.80 |
| ±4 半音 | 7.6 | 7.61 |
| ±6 半音 | 11.4 | 11.41 |

（系数是 1.902 而不是 2 —— `A·sin(θ)` 服从反正弦分布，p90−p10 = 1.902A。）

**教训**：测量脚本必须共用同一份估音器。`measure-ref-calmness.mjs` 一度复制了一份
带 bug 的副本，把参考音频的音域虚报了一倍。**凡是要跨脚本复用的算法，先写自检。**

### 参考音频库：情绪纯度比数量重要


40 条，来自《原神》中文语音包，按 8 类 × 每类 5 条：

| 类别 | 桶内素材 | 说明 |
| --- | --- | --- |
| 平静 | 122 | 中性叙述、随口应答 —— 闲聊的默认语气 |
| 开心 | 34 | 真的高兴（不是嘲讽） |
| 得意 | 68 | 端着架子、炫耀、俏皮挑衅 |
| 温柔 | 42 | 关心、安慰 |
| 无奈 | 62 | 无语、放弃抵抗、叹气 |
| 生气 | 18 | 真的不满、拌嘴 |
| 难过 | 17 | 失落、委屈 |
| 惊讶 | 26 | 意外、吃惊 |

音频**已经收进 `assets/voice/clips/`**（23 MB），不再依赖 `<语音包目录>`。
`library.json` 里还留着 `srcFile` 记录出处，方便以后扩库时回溯。

**建库踩过的两个坑**（都在 `scripts/build-voice-library.mjs` 里留了注释）：

1. **打分公式把最不该选的顶了上来。** 原来是 `score = confidence * 10 + quality`，
   而 `confidence` 是**语气强度** —— 「平静」按定义就是低强度，于是这个公式
   系统性地优先挑出最不平静的那几条：「平静」桶 4 条里有 2 条其实是「无奈」，
   其中一条是「（几百年间我做了那么多调查，可没有任何突破预言的希望…）」，
   一段绝望独白。用它当参考去念「嗯，我在听」，听起来就是在哭。
   现在强度打分**方向按类别区分**：平静要淡，生气要强。

2. **「哪些细标签能进同一个桶」和「这个桶能不能用」是两件事。**
   `MAP` 决定谁能进桶，`PURE` 决定谁**能用**。混着用会让参考音频把错的语气传染出去。
   同理，句式覆盖也要**先保证问/叹/陈述/省略四种句尾各有至少一条** ——
   选择器最强的信号就是句尾对齐（权重 4.0）。改成这样之后句式命中率 89% → 100%。

**为什么从 6 类拆成 8 类**：「得意」(68) 和「无奈」(62) 本来是并进 开心 / 平静 的，
但它们是芙宁娜最有辨识度的两种语气，合并两边都变味：

| 她的台词 | 6 类时 | 拆开后 |
| --- | --- | --- |
| 「又走？你这两句话是故意气本神的吧」 | 判成 [生气]，配到审讯腔「难不成你敢在这个地方做伪证？」 | [得意]，配俏皮挑衅 |
| 「哼，这种料理得不到我的认可」 | 判成 [开心]，配真笑「哈哈哈哈」 | [得意]，配端架子 |
| 「唉，看来要稍微节约一点…」 | 判成 [平静]，配中性叙述 | [无奈]，配叹气 |

重新构建：`npm run voice:build`（= `vendor-voice-clips.mjs` + `build-voice-library.mjs`）。
加了 `--per=N` 可以改每类条数，默认 5。

## 模型（Live2D）

当前用的是 **芙宁娜**（原神）的同人 Live2D，来源：

> **【無料配布Live2Dモデル】原神 フリーナ【VTS対応】** —— 作者 狐宮静商店
> https://booth.pm/ja/items/5876181 （免费配布，介绍视频 https://youtu.be/8-lINxFHcvw ）

**授权条款（作者原文）：** ① 著作权归 miHoYo；② 可用于制作原神相关影像，禁止政治宣传，遵守官方二次创作规定；③ **禁止商业直播使用、禁止二次配布**。所以模型文件**绝对不能提交进 git**（`assets/models/` 已在 `.gitignore` 里）。

### 装一个新模型

```bash
node scripts/install-model.mjs "<模型目录>" <目标名字> --set-default
```

比如本机这份：

```bash
node scripts/install-model.mjs "<你的Live2D模型目录>" Furina --set-default
```

这个脚本做三件手改容易漏的事：

1. **文件名转 ASCII。** 模型里的文件名常带中文，而渲染层是通过自定义 `pet://app/...` 协议加载的 —— 中文要经过 URL 百分号编码再解码，不同环节对编码的处理不完全一致。与其赌，不如统一转 ASCII，并同步改 `model3.json` 里所有引用。
2. **补 Expressions / Motions 登记。** VTS 用的模型经常只在磁盘上放着 `.exp3.json` / `.motion3.json`，而 `model3.json` 里**没有**这两段（VTS 读它自己的 `.vtube.json` 热键配置）。但 pixi-live2d-display 只认 `model3.json` —— 不补的话表情和动作全用不了。这次芙宁娜的 4 个表情就是这么找回来的。
3. **剔掉 VTS 专属文件**（`.vtube.json`、`items_pinned_to_model.json`）。

单个动作的模型会被登记成 `TapBody` 而不是 `Idle` —— 只有一个挥手动作放进 Idle 会变成每隔几秒挥一次手，很怪；放 TapBody 就是「戳她一下，她挥手」。

### 这个模型的两个坑

**① 原生表情很少，而且不是标准参数。** 它只有 4 个表情开关，每个只是把某个自定义参数置 1：
`Param12 脸红` · `Param11 爱心眼` · `Param13 生气` · `Param15 挥手`（挥手是动作不是表情）。
所以情绪映射只接了 4 个：

| 情绪 | 用模型自带表情 | 靠标准参数推 |
| --- | --- | --- |
| 得意 | `heart-eyes`（爱心眼） | + 抬下巴、嘴角上扬 |
| 开心 / 温柔 | `blush`（脸红） | + 眼睛微笑、嘴型 |
| 生气 | `angry` | + 压眉、嘴角下垂 |
| 平静 / 难过 / 惊讶 / 无奈 | —— | 全靠 `ParamEyeLSmile` / `ParamBrowLY` / `ParamMouthForm` 这些标准参数 |

它**没有** `ParamCheek` / `ParamBrowLAngle` / `ParamBrowLX`，所以 `face.js` 的预设一个都没用它们
（眉毛角度改用「变形」近似）。缺参数时 `apply()` 会单独跳过，不会整段失效。

**② 没有 idle 动作，而且贴图是 4096²。**

- 没有 idle 动作 → 光靠物理演算会像张静止图。所以 `pet.js` 在帧循环里叠了一点**极慢的呼吸和摇头**（`ParamBreath` + `ParamAngleX/Y/Z` 微小正弦）。用 `add` 而不是 `set`，不会覆盖掉鼠标跟随写入的角度值。角色文件里 `live2d.idleLife: false` 可以关掉。
- 两个 4096² 贴图解码后要 **134 MB 显存**，而窗口最宽也就 828px（180% 缩放）—— 纯浪费。**降到 2048 后待机 CPU 从 59% 掉到 26.6%（单核），内存 661→478 MB**。原图备份在 `assets/models/Furina/furina/orig/`。降采样已经写进 `install-model.mjs`（`--keep-texture-size` 可跳过）—— 不写进去的话每次重装都会悄悄退回 4096。

### 怎么触发动作

| 操作 | 触发什么 | 谁负责 |
| --- | --- | --- |
| **点一下她** | 挥手 + 随机台词 | `tap()`，台词在 `characters/<id>.json` 的 `tapLines` |
| 鼠标移到她身上 | 视线和头跟随 | `followPointer()` → `model.focus()` |
| 跟她说话 | 嘴型 + 情绪表情 | 音量包络 + `face.js` |
| 一直不理她 | 呼吸 + 轻微摇头 | ticker 里的待机微动 |
| `electron . --shot out.png 8000 --tap` | 开发用：截图前自动戳一次 | `--tap` 标志 |

**「点角色」这个功能原本是坏的**，换模型时才顺带发现：

```js
// pixi-live2d-display
set autoInteract(t){ ... t ? this.on("pointertap", Handler, this) : this.off("pointertap", Handler, this) }
```

模型是按 `autoInteract: false` 建的（为了关掉它自带的整窗跟随），而这个开关**正好也是决定要不要注册 `pointertap` 的地方** —— 关掉之后模型也不是 `interactive` 的，`model.on('pointertap', ...)` 那个监听**永远不会触发**。所以之前点她毫无反应。

现在改成挂在项目自己的 `hitTest` 上（和鼠标穿透协调用同一套判定），不再依赖 Pixi 的交互系统。

> 挥手这个动作由**两部分**组成，缺一不可：`wave.exp3.json` 把 `Param15` 置 1（手出现的开关），`wave.motion3.json` 动画 `Param14/16/17`（手的摆动）。只播动作的话手根本不出现 —— 所以 `tap()` 里是「先打表情、再播动作、到点收回」三步。
>
> 另外那个 motion3.json 的 `Meta.Loop` 原本是 `true`（VTS 自己控制播几次），pixi-live2d-display 会**一直循环**挥下去。`install-model.mjs` 装的时候会改成 `false`，`tap()` 里还有一道定时停掉的保险。

## 配置 API Key

**方式一（推荐）：环境变量。** 只要系统里有下面任意一个，就能直接用，不用建文件：

```
DEEPSEEK_API_KEY / OPENAI_API_KEY / DASHSCOPE_API_KEY / ALIYUN_API_KEY / ZHIPUAI_API_KEY
```

> 查找顺序：`config.json` → 进程环境变量 → Windows 用户级环境变量（直接读注册表）。
> 读注册表这一层是为了覆盖"环境变量是后来才设的，当前进程没继承到"的情况，
> 省得你为了让它生效去注销一次。

**方式二：`config.json`。** 复制模板再改：

```bash
cp config.example.json config.json
```

```jsonc
{
  "baseUrl": "https://api.deepseek.com/v1",
  "apiKey": "",                 // 留空就走环境变量；再没有就进演示模式
  "model": "deepseek-chat",
  "systemPrompt": "你是一只桌面小宠物…"
}
```

改完**切回桌宠窗口会自动重新载入**（不用重启）。右上角 ⚙ 可以直接打开这个文件。

**不填 Key 也能启动** —— 会进「演示模式」，回复是本地预置的，用来先看形象和交互。

## 操作

界面从下往上只有两样东西：**输入栏（含所有按钮）** 和 **字幕**（显示最近一轮），其余空间全给角色。
历史记录是浮层，默认藏着。

| 操作 | 说明 |
| --- | --- |
| 拖输入栏最左边的 ⠿ | 移动窗口 |
| **点一下角色** | **挥手 + 随机台词**（只在她身上有效，点别处直接穿透到桌面） |
| 鼠标移动 | 角色视线和头跟着你 |
| 回车 / 发送 | 发消息。开了语音时，文本流完她就开始念 |
| Esc / 停止 | 中断当前生成（同时掐掉正在念的话） |
| 🔊 | **语音开关**。亮蓝=开着且后端在线；⚠️=开着但连不上 GPT-SoVITS；灰=关着。点击会写回 config.json |
| **滚轮（在角色身上）** | **放大 / 缩小** |
| **Ctrl + 滚轮（任意位置）** | **放大 / 缩小** |
| **Ctrl + `+` / `-` / `0`** | **放大 / 缩小 / 复位** |
| `≡` | 打开历史记录（浮层） |
| 🧠 | 记忆面板：查看 / 整理 / 列出 / 清空 |
| `⚙` | 打开 config.json |
| `▾` | 收起输入区，只看角色（底部留一个小 `▴` 展开） |
| `−` | 隐藏 / 显示桌宠（同 `Ctrl+Shift+P`） |
| `×` | 退出（同 `Ctrl+Shift+Q`） |

缩放范围 **60% – 180%**，锚点在右下角，**会自动记住**。
缩放同时改窗口尺寸和网页缩放倍率，并且**会重新同步画布分辨率**——
否则放大后画布像素没变却被拉大显示，看起来就是糊的（这就是之前"分辨率太低"的原因）。

**鼠标穿透**：窗口默认整窗穿透，点击直接落到桌面上；只有压在**角色轮廓**或 UI 上时才接管鼠标。
靠 Electron 的 `setIgnoreMouseEvents(true, {forward: true})` 实现——它能在穿透状态下继续收到 `mousemove`。

    ├── import-card-lore.mjs     抽卡的世界书 → 翻中文 → assets/lore/
    ├── probe-models.mjs         探测可用模型名
    └── bench-models.mjs         对比各模型的延迟与 token 消耗
```

### 三个值得记住的实现决策

**1. 用自定义 `pet://app/` 协议，而不是 `loadFile`**
Live2D 的模型和贴图是 XHR 加载的，Chromium 默认禁止 `file://` 页面 XHR 其它 `file://` 资源。与其关掉 `webSecurity`，不如注册一个规范协议来源，安全和 CSP 都保得住。

**2. API Key 只留在主进程**
渲染层通过 IPC 请求聊天，永远拿不到 Key。`preload.js` 是一份白名单，不开 `nodeIntegration`。

**3. 口型覆盖必须在帧循环最后**
模型的待机动作每帧都会写 `ParamMouthOpenY`。所以说话时的嘴型覆盖挂在 `PIXI.Ticker.shared` 的 `LOW` 优先级上（模型自己是 `NORMAL`），保证排在它后面；否则嘴会被动作冲回闭合。表情参数叠加也在同一个 ticker 里 —— 同理，排在动作之后才不会被冲掉。

**4. 语音的 wav 必须和页面同源**
试过给音频单开一个 `pet://voice/` host，看着更干净，但那是**另一个 origin**，
被 CSP 的 `connect-src 'self'` 直接拒掉。所以走 `pet://app/.userdata/tts-cache/…`；
协议处理器只对这一个子目录放行，同目录下的 `facts.json` / `history.json` / `embeddings.json` 一律 403。

### 两个容易踩的坑（都已处理）

**PixiJS 6 要 `new Function()` 编译着色器**，会被严格 CSP 拦住并抛
`Current environment does not allow unsafe-eval`。
解法不是关 CSP，而是加 `@pixi/unsafe-eval`（已 vendor，必须紧跟 `pixi.min.js` 之后加载）。

**pixi-live2d-display 0.4.0 只兼容 PixiJS 6**，装成 7 / 8 直接报错。

**4. 帧率要按活跃度分档（省 CPU 的大头）**
Pixi 的 ticker 默认无条件 60fps 渲染，Live2D 每帧都算物理和动作——哪怕她只是站着。
实测空闲时白烧**约 100% 单核**（渲染进程 78% + GPU 进程 23%，i5-12400F 上是任务管理器 8.3%）。
现在分档：说话 / 刚交互 60fps，长时间没人理降到 30fps；窗口隐藏时直接停 ticker。

**结果：约 100% → 约 20% 单核（任务管理器 8.3% → 1.7%）。**

档位可以在 `config.json` 里调（`fpsActive` / `fpsIdle`）。觉得掉帧就把 `fpsIdle` 也设成 60；
想更省电就调低。**别用降分辨率的方式省 CPU** —— 见下面那条对照结论。

配套的两个坑：
- **鼠标事件不能照单全收**。开了 `setIgnoreMouseEvents` 的 `forward: true` 之后，鼠标停在窗口上
  也会持续送坐标不变的事件，把帧率永远顶在高档（表现为档位反复横跳）。
  现在只有真正移动超过 2px 才算活跃。
- **`backdrop-filter` 和画布上的 `filter: drop-shadow()` 都删了**。它们要在透明窗口上逐帧重算，
  实测能顶掉约 10% 单核。

> **反直觉的对照结论**：把 `resolution` 从 `devicePixelRatio` 降到 `1`、并关掉 `antialias`，
> CPU 几乎没变（15.5% → 15.3%）。说明剩下的开销**不是 Live2D 渲染成本，而是 Electron 合成
> 透明置顶窗口的固定开销**。所以不要为了省 CPU 牺牲画质 —— 该调的是帧率，不是分辨率。

**5. 缩放之后必须重新同步画布分辨率**
`window.devicePixelRatio` 会跟着网页缩放倍率变，但 Pixi 的 `resolution` 只在建
`Application` 时读一次。不同步的话，画布实际像素没变却被拉大显示 → **糊**。
实测值（修复后）：

| 缩放 | 画布 CSS | 画布实际像素 | devicePixelRatio |
| --- | --- | --- | --- |
| 1.0 | 463×720 | 579×900 | 1.25 |
| 1.5 | 463×720 | 868×1350 | 1.88 |

## 记忆是怎么设计的

拆成**两个互不相干的模块**，因为它们回答的是两个不同问题：

| 模块 | 回答的问题 | 存储 |
| --- | --- | --- |
| `src/memory.js` | **「他是什么样的人」** —— 偏好、身份、关系 | `facts.json` + `embeddings.json` |
| `src/history.js` | **「我们聊过什么」** —— 对话本身的压缩 | `history.json` + `archives.json` |

设计参考了 **N.E.K.O.**（B站「猫娘计划」，Apache-2.0）的五维记忆、**OpenViking**（火山引擎）的 L0/L1/L2 分层上下文，以及 **ReMe**（原 MemoryScope）的 RRF 混合召回 —— 但按个人规模大幅裁剪。

### 一、事实记忆（memory.js）

```
一次对话结束
   ↓  只入队，不做任何网络请求（前台永不阻塞）
pending.json
   ↓  空闲 30 秒后 / 或积压满 8 轮 → 后台整理
抽取「持久事实」（把已知道的事实一起给模型，从源头避免重复）
   ↓  哈希 → bigram 相似度 → 向量余弦+包含关系 三重去重
facts.json + embeddings.json
   ↓  新对话时：BM25 ⊕ 向量，RRF 融合
注入 system prompt 的【你记得关于他的事】
```

**抄了什么、砍了什么**

| 原设计 | 我这边 | 理由 |
| --- | --- | --- |
| 前后台分离，前台只落盘、抽取延后 | ✅ | 最值钱的一条：**绝不让用户在等回复时等抽取** |
| 事实带 subject / importance | ✅ | 召回时能用重要性兜底 |
| BM25 + 向量 + RRF 融合 | ✅ | 单靠任一种都有盲区：BM25 对同义改写无力，向量对专名/数字不敏感 |
| 抽取失败保留待重试 | ✅ | 失败就留着 pending，下次再试 |
| 反思层（reflections） | ❌ | 「由多条事实合成更高层理解」有价值，但优先级低 |
| 证据衰减、人格提升 | ❌ | 解决「改主意后旧记忆退场」。见下方「还没做」 |
| outbox 幂等重放 / 事件溯源 | ❌ | 一个 `pending.json` 在这个规模完全够 |

**几个自己踩出来的细节：**

- **字符 bigram 分词**。中文没空格，bigram 零依赖又够用，不用引 jieba。
  顺便说：调研里提到「中文无空格分词会击穿 BM25」—— 那说的是标准空白分词器，bigram 正好绕开这个坑。
- **相似度阈值 0.72 是实测的**：`"最喜欢的颜色是蓝色"` vs `"最喜欢颜色是蓝色！"` = 0.73（该合并）；
  `"喜欢蓝色"` vs `"喜欢蓝色和绿色"` = 0.63（不该合并）。**宁可漏合并也不误删**。
- **向量去重不能只靠阈值**。`Qwen3-Embedding` 的相似度基线偏高（不相关的两句话也有 0.5+），
  所以合并规则是「余弦 ≥ 0.94」**或**「有包含关系且余弦 ≥ 0.85」。
  降阈值到 0.9 是危险的 —— `"喜欢蓝色"` 和 `"喜欢绿色"` 余弦也很高，那是**改主意**不是重复。
- **根治重复的办法是在提示词里给「已知事实」**，而不是事后靠相似度合并。
  实测：不给清单时重复喂同一段对话会新增 3~6 条；给了清单后**新增 0 条**。
- **查询向量化有超时兜底**（默认 800ms）。实测 8B 模型中位只要 111ms，但尾部能飙到 2846ms ——
  对桌宠来说偶发卡顿比稳定慢更难受。超时就**这一轮退回 BM25**，不让人干等。

### Embedding 模型怎么选的

写了个检索质量基准（`node scripts/bench-embedding-quality.mjs`）：10 条事实 + 10 个**刻意避开
事实原词**的查询（其中 7 个与目标事实零 bigram 重叠，纯靠语义），看正确事实能不能排到第一。

| 模型 | 维度 | Top1 | MRR | 查询中位 | **最慢** | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **Qwen3-Embedding-0.6B** | 1024 | **80%** | 0.831 | **62ms** | **72ms** | ⭐ **选它** |
| Qwen3-Embedding-4B | 2560 | 70% | 0.784 | 90ms | 104ms | 更慢，质量没占优 |
| Qwen3-Embedding-8B | 4096 | 70% | 0.765 | 103ms | 249ms（另一轮测到 2846ms） | 更慢，质量没占优 |
| BAAI/bge-m3 | 1024 | 80% | **0.875** | 86ms | **3959ms** | 排序最好但尾部 4 秒，出局 |

**结论有点反直觉：0.6B 在 Top1 上反而比 4B/8B 好**（10 个样本，差距是 1 个查询，不算显著），
但**延迟差异是压倒性的** —— 0.6B 最慢 72ms，几乎零抖动；8B 会偶发 2.8 秒。
再加上向量文件体积差 4 倍（1024 vs 4096 维），0.6B 是明确的选择。

> ⚠️ 这只是 10 个样本的小基准，够用来**排除明显不行的**（比如 bge-m3 的尾部延迟），
> 不足以精确排名。想自己测就改 `scripts/bench-embedding-quality.mjs` 里的 `FACTS` / `QUERIES`。

**换模型时会自动作废旧向量。** 不同模型的向量空间不通用，拿旧向量算余弦**不会报错**，
只会悄悄召回错东西 —— 这种 bug 最难发现。所以 `embeddings.json` 里记了模型名，
载入时对不上就丢弃重算（`node scripts/test-embedding-switch.mjs` 验证这条）。

**存储**：向量文件用紧凑格式（不缩进），1024 维下每条约 9.4 KB，500 条事实约 4.7 MB。

### 二、分层历史（history.js）

解决的问题：只把「最近 N 条原文」塞给模型的话，聊得越久她越不记得前面聊过什么。
而这件事没法靠加窗口解决 —— 上下文总有上限。

```
全部原文 (history.json，界面回看用)
     │
     ├─ 最近 recentCount 条 ──────────→ 原样进 prompt
     │
     └─ 更早的 ──→ 每 20 条切一块 ──→ 每块一段「概览」
                                      │
                                      └─ 块数超过 maxBlocks 时，把最老的几段再合成一段
```

拼进 prompt 时按「从新到旧」装，装到 `contextBudget` 字符用完为止。
于是自然形成**近的详细、远的粗略**，而不是一刀切截断。

**实测效果**（`node scripts/test-history.mjs`）：

| 早期聊过的信息 | 只给最近 N 条 | 最近 N 条 + 档案 |
| --- | --- | --- |
| King Crimson | ❌ 丢 | ✅ 在 |
| 豆豆（猫） | ❌ 丢 | ✅ 在 |
| 小林（女友） | ❌ 丢 | ✅ 在 |
| 数字媒体（专业） | ❌ 丢 | ✅ 在 |

预算 200 字时只放 1 段档案，500 字以上放 2 段，**从不超预算**；档案合并之后老信息也还在。

**两个踩出来的坑：**
- **归档边界不能用时间戳**。同一毫秒内连写多条会撞在一起，边界失效 ——
  实测表现是「最近的原文只取到 2 条，而且全是 assistant」。改用自增 `seq`。
- **必须分块归档**。一次把几百条压成一段，档案层就没有「近细远粗」的层次了，
  单段概览也会糊掉细节。所以单次最多压 `archiveChunk`（默认 20）条。

### 三、时效性 / 矛盾消解（事实会退场）

之前的事实是**永恒的** —— 你说"我现在不喜欢蓝色了"，系统会同时存下
「喜欢蓝色」和「不喜欢蓝色」，召回时两条都注入，她就精神分裂了。

现在每条事实带四个字段：

| 字段 | 含义 |
| --- | --- |
| `validFrom` | 从什么时候开始成立 |
| `invalidAt` | 什么时候失效（`null` = 仍然有效） |
| `supersedes` | 它取代了哪条 |
| `supersededBy` | 它被哪条取代了 |

**写入时**：抽取提示词要求模型在推翻已知事实时，用 `supersedes` 字段指认被推翻那条的**编号**
（已知事实清单是带编号给它的）。收到后把旧事实标记失效，并接上双向链接。

**读取时**：召回**只从有效事实里选**。失效的留在 `facts.json` 里只为可审计和面板展示，
**绝不进 prompt**。

**关键细节**：声明了取代关系的新事实会**跳过 0.72 相似度闸门** ——
否则「改成绿色了」可能因为跟「喜欢蓝色」长得像而被当成重复直接丢掉，修正就丢了。

**实测**（`node scripts/test-temporal.mjs`）：

| 场景 | 结果 |
| --- | --- |
| 改主意（蓝→绿） | 旧的标记失效，双向链接正确 |
| **召回** | 只出「绿色」，**不再同时出现新旧两条** ✓ |
| 否定式修正（"Rust 我放弃了"） | 旧的退场，新的是「用户已放弃学习 Rust」✓ |
| 数据可审计 | 失效条目不删除，保留 `validFrom → invalidAt` 区间 ✓ |
| 老数据迁移 | 没有时效字段的旧事实自动补 `invalidAt: null` ✓ |

### 四、遗忘曲线（事实会淡出，但不会被删）

有效事实之间原来永远等权 —— 三年前和昨天一样重。现在每条事实有一个**强度 ∈ [0.2, 1]**：

```
强度 = 0.5 ^ (距上次被用到多少天 / 半衰期)
半衰期 = 基础值(看重要度) × (1 + ln(1+被用次数) × 0.6)
```

| 重要度 | 半衰期 |
| --- | --- |
| 5（核心身份） | 180 天 |
| 4（稳定偏好） | 90 天 |
| 3（一般信息） | 30 天 |
| 2 / 1 | 14 / 7 天 |

**两个关键设计：**

1. **锚点是「上次被用到」而不是「创建时间」** —— 被召回注入过就算用到，会**回血**。
   这实际上就是**间隔重复**：经常被需要的事一直强，没人问的事慢慢淡出。
   实测：90 天前创建但昨天刚用过的事实，强度 0.996（几乎满血）。
2. **只降权，不删除**。强度作为召回排序的乘数，最低也有 0.2 ——
   她仍然"记得"，只是不会再主动提。数据永远在 `facts.json` 里。

```
强度 30 天 → 0.794    90 天 → 0.500    365 天 → 0.200（触底）
```

召回计数**延迟 5 秒落盘**，不会每说一句话就写一次文件；退出前 `flush()` 补写。

### 五、开环记忆（她会记得问你结果）

你说"我明天下午三点有面试"，她第二天该问一句"面试怎么样"——这才像真的在意。

抽取时如果发现**有明确时间点的未来事件**，会额外抽一个 `followUpAt`。
到点之后，下一次对话会自动注入一段：

```
【他之前提到还没了结的事】
用户 2026-09-21 周一下午三点有一场面试（2 小时前）
（可以自然地关心一下后续，但别硬拗、别说教、一次只提一件）
```

**防复读机的三条约束：**
- 一次只提**一件**（不是把攒的全倒出来）
- 每件最多主动提 **2 次**，提够自动了结（`closedAt`）
- 一次会话里只提一遍

`followUpAt` 的解析做了防护：必须在将来（>5 分钟）、不超过 180 天，否则忽略。
模型被要求给 ISO 格式，但也兜底认 `明天 17:00` / `后天上午 9:30` 这类写法。
**坏时间戳宁可不开环，也不要把记忆搞乱。**

**实测**（`node scripts/test-decay-loop.mjs` + 端到端）：

| 场景 | 结果 |
| --- | --- |
| 衰减曲线 | 30/90/365 天 → 0.79 / 0.50 / 0.20 ✓ |
| 回血 | 90 天前创建但昨天用过 → 0.996 ✓ |
| 只降权不删 | 三条同主题事实都还在，只是排序不同 ✓ |
| 到点才提 | 未来的不提、已了结的不提 ✓ |
| 提够收敛 | 提 2 次后自动 `closedAt`，不再念 ✓ |
| 坏时间戳 | 过去 / 5 分钟内 / 一年后 / 纯垃圾 全部忽略 ✓ |
| 端到端 | 说"明天下午三点有面试" → 抽出 `followUpAt=明天15:00` ✓ |

### 六、还没做（诚实清单）

- **记忆处理不是本地的**。抽取、摘要、向量化都会把内容发给对应服务商
- **开环的了结是自动的**（提够 2 次）。还没有"从对话里识别出结果"来主动了结
- **没有好感度 / 关系状态**（用户明确说以后再做，且属于玩法而非准确性）

| `electron . --selftest "你好" 30000` | 在真实窗口里发一条消息，等她说完整段，打印落盘结果 + **语音链路体检** |

`--selftest` 除了验证「发送 → 流式回复 → 落盘」，还会并行跑一个**语音观察员**：
等她说第一句时开始采样 `ParamMouthOpenY`，并在嘴张得够大时定格截图。
输出长这样：

```
[tts] 情绪判定 温柔（来源 tag）
[selftest] 听到她开始说话了
[selftest] 嘴型采样 0.14 0.07 0.01 0.00 0.25 1.00 1.00 1.00 …
[selftest] 嘴型范围 0.000~1.000，变动 34/52 次 → ✅ 嘴在跟着音频动
[selftest] 说话中的截图 → .userdata-dev\speaking.png
[selftest] 渲染层实播 2 段 / 累计 9240ms 音频 / 解码失败 0 / 包络峰值 1.000 / AudioContext=running
```

观察员必须和对话**并行**跑：总结（记忆整理）本身要一次 LLM 调用好几秒，
等它回来时语音早就播完了，采样只能采到空气。

### 已知限制

- 没有语音**输入**（打字为主，这是刻意的）
- 不能唱歌 —— L3
- 模型是同人免费配布的 Live2D（狐宮静商店），不是米哈游官方素材；只有 4 个原生表情，其余情绪靠标准参数推
- 语音服务要常驻一个 Python 进程，占约 4.5 GB 显存
- 合成一句约 1.6~2 秒；流水线能让她早点开口，但第一句仍要等
- **语气偏戏剧化，而且推理阶段改不掉。** 芙宁娜 v4 权重是在 1139 条游戏剧情/战斗台词上
  微调的，模型学到的就是舞台腔。实测换参考、调 `temperature`、调 `sample_steps`
  都压不平（输出音域始终落在 8~10.5 半音）。要改只能重新微调，或接受这个风格。
- **参考库本身也全是"在演"的素材。** 122 条「平静」候选里音域最小的也有 6.05 半音，
  中位 9.35 —— 没有一条达到自然平静说话的水平（3~6）。数据集里根本不存在平淡的录音。
- 命中判定用的是模型包围盒，不是像素级轮廓；角色的透明边角仍会挡鼠标
- 只适配了单显示器
